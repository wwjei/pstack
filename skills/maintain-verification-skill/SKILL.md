# 维护验证技能

应用一变，功能地图就开始腐烂。本技能是 `/create-verification-skill` 生成的技能（或任何带功能地图的项目本地验证技能）的维护循环。较真的单位是功能，不是每个句子：每个功能文件都从源码覆盖，每个功能都实跑一遍，但不必把每条列表项都上终端跑。

## 结果

选一个，并说明选的是哪个：

- **clean（干净）** - 每个功能都拿到了源码和实跑覆盖；没有值得发布的改动。不开分支，不开 PR。
- **changed（有改动）** - 一个 PR 发布经过证明的文档、验证工装或地图修正。
- **blocked（受阻）** - 覆盖没能完成，或经过证明的修复无法安全发布。说清楚到底是什么挡住了。

## 编辑范围

只编辑验证技能自己的目录（它的 SKILL.md、features/，以及它拥有的验证工装脚本）。运行期间绝不编辑产品代码：地图描述的行为应用不再做了，要么是文档漂移（修地图），要么是产品回归（报告它，别在文档里糊弄过去）。

## 流程

0. **定位目标。**找到要维护的验证技能：正文里有启动/驱动小节和功能地图的项目本地技能（通常在 `Hermes profile skills directoryverify-*/`）。候选有好几个 → 问用户要哪个；一个都没有 → 停下，指向 `/create-verification-skill`，不要凭空造一个目标。

1. **索引清理。**读功能地图的 README，用 glob 列出同级文件。修掉缺失、多余、重复或失效的条目。轻量处理；不生成盘点清单。

2. **源码波次。**每个功能文件派一个只读子代理，并发启动。每个子代理从源码解释「这个用户可见功能是怎么工作的？」，标出疑似文档漂移并附引用，返回一份简明的实跑验证配方。子代理绝不驱动应用，绝不编辑文件。返回形状：功能摘要 / 源码入口 / 疑似漂移或无 / 一份配方。

3. **核对。**每个功能文件都有一份返回的摘要。把重叠的配方合并，落到尽可能少的应用状态上。抽查被引用的漂移；干净的论断不必重新证明。扫一遍近期改动，找地图漏掉的用户可见交互面 - 说某个交互面缺失之前，先拿到具体的源码路径。

4. **实跑轮。**源码看着干净也必须跑。协调器负责全部驱动；遵循验证技能自己的启动模型 - 服务器和 UI 用一个长活实例串行驱动，短命 CLI 每次驱动开一个全新的隔离会话（由该技能的启动小节决定，不由本小节决定）。每个功能至少操作一遍，整轮无论遇到什么失败都守住三条不变量：(1) 绝不驱动一个自上次出意外后没做过健康检查的实例 - 首次驱动前做健康检查，以会话为单位时每个新会话都做，任何一次驱动失败后再做；健康检查看不到失败的地方（进程健康但 UI 卡死），重置到已知状态或重新启动，别抱侥幸；(2) 已采集的证据在每次清理后都存活，到指明的位置核实，不是想当然；(3) 驱动启动的东西，一样都不许活过这次驱动的用处 - 失败迭代的残留都要清掉，不管会话是卡住、退出还是共享（共享实例清残留，不清实例）。技能漂移导致的健康检查失败就是漂移：在编辑范围内修好，重试一次 - 只重启被修复弄失效的东西，别的不动 - 然后才能把这一轮判为 `blocked`。到不了的功能，只有附上具体前置条件（认证、授权、操作系统、外部状态）和尝试过的路径，才能标 `verified-unreachable`；地图漏了这个前置条件，就是漂移。分诊来的任何验证工装修复，发布前都要重新实跑。最终拆除放在本次运行最后一次驱动之后 - 包括那些重新证明 - 让任何东西都活不过这次运行（证据按技能规定保留）。

5. **分诊。**用户视角描述错误或缺失 → 文档漂移，修掉。行为正常但验证工装驱动不了 → 验证工装缺口，修掉；验证工装修复遵循与生成时相同的辅助脚本规则（脚本可执行，调用方式写在技能正文里）。应用行为真的坏了 → 产品缺口；记下来交给用户，别放进这个 PR。

6. **发布或停下。**changed：一个 PR 装经过证明的修正，先把每个改过的文件重读一遍。clean 或 blocked：不开 PR，如实报告结果和覆盖情况。

把简明的运行笔记（覆盖了哪些功能、不可达的前置条件、确认的漂移、结果）记在临时位置；不要提交它们。
