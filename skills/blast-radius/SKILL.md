# Blast radius

在发布前，找出一个改动在别处弄坏了什么。用于「X 的影响半径」「这可能弄坏什么」，或审查一个你还信不过的小 diff。

`how` 和 `why` 的搭档。`how` 告诉你代码做什么。`why` 告诉你它为什么长成那样。影响半径告诉你它在别处弄坏什么。

列出调用方不是这份工作。代理一秒就能 grep 出来。这份工作是 grep 不会给你看的那些破坏。

## 别信你自己写的报告

一份听起来对的影响半径报告毫无价值。无论真假，它读起来都令人信服。所以别把报告交回去。找出整件事依赖的那一两个事实，靠跑代码证明它们。

### 你有多确定

对改动安全性依赖的每个事实，在代价允许的范围内沿这张清单尽量往下走，并说清停在哪。

1. 你这么说。单独看毫无价值。
2. 你指到了那一行。一个真实的 `file:line`，或库自己的源码。
3. 你证明了坏情况不会发生。你一步步走过那个失败，它到不了。
4. 你跑了它。一个脚本或测试，调用真实代码，你错了就大声失败。
5. 你在运行中的应用里复现了它。

第 4 步通常是一个小脚本，导入应用发布时用的同一个库，调用你担心的那个确切函数。

## 步骤

1. 读这个改动。diff、它新增/改动/删除的符号、它现在做得不一样的地方，包括 diff 没明说的那部分。用 `why` 的第 2 步拉取 PR 和提交。
2. 找出它之所以安全的那一个事实。大多数看起来危险的改动，安全都系于一个事实，比如「这个调用只丢弃已经死掉的缓存条目，别的什么都不做」。找出那个事实。它成立，大多数危险情况就一次性排除。把时间花在这，不是一长串「可能」上。
3. 看 grep 停下的地方。读你调用的库的源码，查它的锁定版本和任何本地补丁。弄清东西什么时候跑：微任务、卸载与拆除、Solid 与 React。追符号搜索漏掉的东西：API 返回的 JSON、一个 DB 列、一种传输格式、另一种读同样字节的语言、一个功能开关、下游三跳的代码。
4. 对每个风险诚实。给它一个真实的发生概率和真实的代价。留下你确认的风险。把你查过并排除的单独列。规则跟 `why` 一样。引用真实的 `file:line`，一次什么都没找到的搜索仍然是答案，绝不编造调用方或 API。
5. 证明那一个事实。写一个跑真实代码的脚本或测试，跑它，把发生的事贴出来。
6. 大或广的改动，把它当作 `arena` 跑。问几个模型同一个问题，合并答案。不同模型抓到不同的真实 bug。

## 交回什么

- **它做什么。** 改了什么，包括不明显的那部分。
- **它之所以安全的那一个事实。** 说出来，说你把它走到了哪一步，摆出证明。证明不了，就写「未证明」。
- **风险。** 每条点名它怎么坏、`file:line`、多可能多严重、怎么查。要紧的那些，贴出证明。
- **已排除。** 你查了什么，为什么没问题。
- **合并之前。** 能抓到真实 bug 的最便宜的测试或复现，包括你写的那个脚本。

经 `unslop` 过一遍，引用真实代码，去任何公开地方之前剥掉所有私密内容。

**回复：** 上面那份报告，那一个安全事实要么已证明，要么标记为未证明。
