# 生成形式化验证技能

测试检查的是有人想到要写的那些情况。形式化验证检查声明范围内的每一种情况：模型里步骤的每一种顺序、某个界限内的每一个输入，或每一个输入。本技能找出仓库里最在乎这一点的部分，验证它的一条性质，并留下一个项目本地技能，让下一个代理能对着这条性质检查改动。那个技能是写给这样的代理的：在改动中途毫无铺垫地直接读它，从没接触过你的工作。用户必须能信任结果并据此行动，不需要学那门验证语言。

## 从代码里选目标

从代码库里找答案，只有观察不到的才问用户。用户点名了某个区域或缺陷，就从那里开始。

好目标是代码许下的承诺，打破了会伤害用户，而测试很少覆盖到打破它的情况。选仓库里这类目标中最强的一个，不是最容易验证的那个。

## 让问题选工具

选能以最低成本回答问题的工具：模型检查器、证明助手、基于 SMT 的验证器，或别的工具。事件会不会以糟糕的顺序发生，这类问题通常适合对设计的小模型跑模型检查器，任何语言下默认都用 TLA+。代码本身对每个输入是否行为正确，比如内存安全、溢出或数据结构不变量，通常适合直接跑在代码上的验证器。没有验证器能跑在这门语言上，就直说，并用生成的输入测试真实代码，而不是给函数手工建的模型。必须在任何规模下都成立的性质，界限不够用，可能需要证明。优先选仓库开发者装得上、跑得起来的工具，并告诉用户你为什么选它。

## 什么算好

- **忠于代码。**模型或证明的每一部分都指向审查者打得开的代码。验证当作一个不可分步骤的东西，在代码里也是一个不可分步骤。名字来自这个仓库。
- **能失败。**从没见它失败过的检查什么都证明不了。让每条性质在它守护的代码的坏变体上失败一次，比如删掉一个检查或调换步骤顺序的变体。
- **发现项就是发现项。**当前代码打破性质时，用代码自己的说法报告它，附上反例。不要为了通过而削弱性质或模型，用户没要求就不改产品代码。
- **对范围诚实。**说清验证了什么，在哪些界限和假设下，漏掉了什么。一次通过覆盖的是模型或界限，不是整个系统。
- **离了工具也读得懂。**性质和危害各用一句大白话陈述。反例讲成一小串步骤，用代码里的说法。
- **重跑便宜。**一条命令，一个可复现的工具版本，一次足够短的运行，短到下一个代理愿意在每个相关改动上都跑它。
- **跟代码同步。**记下每个检查覆盖哪些文件和函数，以及你最后一次确认验证描述的还是它们的那个提交。被覆盖的代码在那个提交之后变了，下一个代理就能看出验证需要再看一遍。

## 生成验证技能

写一个项目本地技能，frontmatter 点明区域和何时使用。没有 frontmatter，技能永远不会注册。只凭这份技能，下一个代理必须能判断改动是否碰到被验证的代码、跑检查、分清真实缺陷和建模错误，并在改动是有意为之时更新验证。把覆盖记录和同步提交放进技能，并告诉下一个代理：只有确认验证描述的还是新提交处的代码，才能把同步提交往前移。用这个仓库真实的命令、路径和名词，不留占位符。

## 交付前先证明

像下一个代理那样，把生成的技能完整走一遍，对象是一个在真实代码里打破性质的临时改动。它必须抓住这次破坏。然后丢掉临时改动，确认检查回到起点：通过，或只在你将要报告的那些发现项上失败。从没跑过的验证技能是草稿。技能漏掉了破坏，或某一步跑不起来，修技能或修验证，不是修临时改动。

## 交付

告诉用户你验证了什么，用了哪个工具、为什么，界限是什么，检查用大白话讲发现了什么，怎么跑，以及不覆盖什么。只有确实发现了相近的目标，才建议第二个目标。把用户指向 `pstack:maintain-formal-verification-skill`，在没有重新检查的改动之后，靠它把验证拉回正轨。
